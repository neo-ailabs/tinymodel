## 1. 模型架构深度拆解（基于 `config.json`、GGUF 头部与 `inkling2.cpp` 源码）

`Inkling-2-Mini` 并非传统的线性堆叠 Transformer 或普通 MoE，而是集成了**三遍循环共享核心（Looped Core）+ 128 选 8 稀疏 MoE + 无 RoPE 相对位置偏置 + 因果短卷积 + 深度块注意力残差 + DSpark 分块投机器**的异构架构：

| 维度 | 实测参数（GGUF 元数据 / `config.json`） | 对推理引擎的关键影响 |
|---|---|---|
| **总参数与激活参数** | 物理总参数 **26.07B–26.2B**；单遍激活 **3.4B**；因中间层循环 3 遍，每 token 等效激活 **5.4B** | **磁盘/显存容量受 26.2B 物理权重约束，但单步算力与访存量仅相当于 ~5.4B 稠密模型** |
| **物理层与逻辑层拓扑** | 共 **24 层物理权重**，展开为 **48 层逻辑评估**：<br>• `Prelude`（层 `0..5`）：执行 1 遍（6 层）<br>• `Looped Core`（层 `6..17`）：共享权重循环执行 **3 遍**（`12 × 3 = 36` 层，占总逻辑层数的 **75%**）<br>• `Coda`（层 `18..23`）：执行 1 遍（6 层） | **显存卸载策略决定生死**：层 `6..17` 每生成 1 个 token 被读取 3 次，必须最高优先级常驻高带宽显存；层 `0..5` 与 `18..23` 仅执行 1 次 |
| **跨遍门控残差控制器** | 第 2、3 遍进入循环核时重置回 `Prelude` 输出，通过 `gate_rank = 64` 控制器 `(1 - tanh(F·h))·cur + tanh(G·h)·msg` 融合上一遍各块隐藏态（`q/k/v/mlp` 四路独立门控） | 48 个逻辑层各自维护独立的 KV 缓存与卷积历史（不能覆盖上一遍的 KV 槽位——主线 `llama.cpp` 在 PR `#32704` 合入前因复用槽位与 NVFP4 缩放问题会输出乱码） |
| **注意力机制（无 RoPE）** | `n_embd = 2304`，`24` 个 Q 头 / `8` 个 KV 头（`head_dim = 128`）；**`rope.dimension_count = 0`**，改用可学习相对位置投影（`d_rel = 16`, `rel_extent = 1024`）+ 对数位置缩放（`floor = 8192`, `α = 0.1`）+ QK L2 范数裁剪（`22.627`）+ 动态 Sink 投影 + 输出 Sigmoid 门控 | 24 层物理层中 **20 层为 `SWA=1024` 滑动窗口**，仅层 `5, 11, 17, 23`（共 **8 次逻辑访问**）为全局注意力；因此 `ctx = 4096` 时全模型 48 逻辑层 F16 KV + 卷积状态仅约 **`292 MiB`**，支持最高 **1M 上下文** |
| **每层 4 路因果短卷积** | `shortconv.l_cache = 4`：包含 `attn_k_conv`、`attn_v_conv`（全局层带输入依赖动态抽头 `conv_proj`）、`attn_post_conv`、`ffn_post_conv` | 每个逻辑层需维护 `(4 - 1) × 6656` 通道的递归卷积状态（48 逻辑层共约 `3.7 MiB`） |
| **稀疏 MoE FFN** | 每层 **128 个路由专家，每 token 激活 Top-8（6.25%）**，无共享专家，`n_ff_exp = 1152`，Sigmoid 门控（`scale = 8.0`），SiTU 激活 + Gate/Up 软截断（`4.0 / 25.0`） | 单 token 解码每经过 1 个逻辑层仅读取 `8 / 128 = 6.25%` 的专家权重，但总常驻体积由全部 128 个专家决定 |
| **原生 `DSpark` 投机器** | `general.architecture = dflash`（`block_size = 8`）：3 层草稿 Transformer + `rank = 256` 递归 Markov 头与置信度头，跨层提取目标模型逻辑层 `[5, 23, 41, 48]` 特征，借用主模型词表（`200,058` 词，对齐填充至 `201,024`） | 单步半自回归并行起草最多 7 个候选 token，对数学推导与代码等高确定性序列收益显著 |

### 实测权重字节分布（`Inkling-2-Mini-UD-IQ1_S.gguf`，共 734 个张量，`7,404.6 MiB`）

| 张量分组 | `UD-IQ1_S` 体积 | `UD-IQ3_XXS` 体积（参考） | 每 token 逻辑访问次数 | 单 token 实际读取流量（`UD-IQ1_S`） |
|---|---:|---:|---:|---:|
| 非专家稠密权重（词表嵌入 + LM Head + 24 层 Attention / Conv / Loop 门控） | `1,166.3 MiB` | `1,290.3 MiB` | Prelude/Coda `1×`，Core `3×`，词表 `1×` | `~1,710 MiB` |
| **循环核专家**（`blk.6..17.ffn_*_exps`，12 层 × 128 专家） | **`3,250.1 MiB`** | **`5,001.8 MiB`** | **`3×`（每次激活 8/128 专家）** | `3 × (3250.1 × 8/128) =` **`~609 MiB`** |
| **外层专家**（`blk.0..5` + `blk.18..23`，12 层 × 128 专家） | `2,976.8 MiB` | `4,819.5 MiB` | `1×`（每次激活 8/128 专家） | `1 × (2976.8 × 8/128) =` **`~186 MiB`** |
| **合计** | **`7,404.6 MiB`（7.23 GiB）** | **`11,123.0 MiB`（10.86 GiB）** | 48 层逻辑评估 | **单步解码仅读 `~2.51 GiB`（约总权重的 34%）** |

> [!IMPORTANT]
> **核心带宽洞察**：虽然 `Inkling-2-Mini-UD-IQ1_S` 文件重达 `7.23 GiB`（26.2B 参数），但由于每层只激活 `8/128` 专家、同时中间 12 层稠密注意力与激活专家被重复读取 3 次，**每生成一个 token 实际需要从内存/显存读取的数据量仅约 `2.51 GiB`**（在 Q4 量化下约 `4.8 GiB/tok`，恰好等价于一个 ~8B Q4 稠密模型的单步访存量，却拥有 26B 容量与 48 层深度）。

- **集成显卡**：Intel UHD Graphics 770（ADL-S GT1，UMA 共享内存，Mesa 25.2.8 ANV）。
- **推理运行时**：Unsloth `llama.cpp` `b12588-mix-c0c3de8`（包含 `inkling2_loop` 循环槽位修复 PR `#32704` 与 `DSpark` 支持）：
  1. **Mesa 25.2.8 RADV Vulkan 后端**（启用 `VK_KHR_cooperative_matrix`）
  2. **ROCm 7.1.1 HIP 后端**（本机针对 `AMDGPU_TARGETS=gfx1200` Wave32 原生编译）
  3. **Alder Lake CPU 后端**（`libggml-cpu-alderlake.so` / `-march=native`）

### 2.2 `tinymodel` 当前直接加载实测与差距定位
执行 `./target/release/tinymodel inspect models/inkling2/Inkling-2-Mini-UD-IQ1_S.gguf` 返回明确诊断：
```text
Error: GGUF '.../Inkling-2-Mini-UD-IQ1_S.gguf': tensor 'output.weight' has unsupported ggml_type 23
```
**原因清楚明确**：
1. **项目范围边界**：[REQUIREMENTS.md](../REQUIREMENTS.md) 第 5 节明确将 `>9B 的模型` 与大型稀疏专家下放列为 Non-goals（M6 仅规划总参数 `≤8B` 的小型端侧 MoE），而 `Inkling-2-Mini` 物理参数达 **26.2B**（BF16 原版 `48.6 GiB`，Q4 约 `14–16 GiB`）。
2. **量化类型缺口**：Unsloth 动态混合量化使用了 `IQ4_XS (23)`、`Q4_K (12)`、`IQ1_S (19)`、`IQ1_M (29)`、`IQ2_XS (17)`、`IQ2_S (22)` 及 `NVFP4 (40)`（`tm-core` 目前已实现 `Q4_0 / Q4_0x4 / Q8_0 / Q5_K / Q6_K / Q2_0 / TQ2_0 / IQ2_XXS / IQ3_XXS / IQ4_NL / BF16`）。
3. **模型图算子缺口**：`tm-models` 尚未实现 `inkling2` 特有的 6 项机制（3 遍循环重置与 `rank-64` 门控消息控制器、无 RoPE 相对位置偏置与动态 Sink、4 路因果/动态短卷积、块深度注意力混合残差 `mix`、`128` 选 `8` `MUL_MAT_ID` 稀疏路由、以及 `dflash/DSpark` 分块投机器）。

> ¹ 默认 `mmap` 模式下 Linux 页缓存会保留文件映射页；在服务模式下开启 `--load-mode none` 后，进程峰值 `RSS` 直降 **42%** 至 **`4,515–5,047 MiB`**。  
> ² `-ot "blk\.(0|23)\.ffn_.*_exps=CPU"`：仅将第 0 层与第 23 层（各执行 1 次的外层）专家放在 CPU，**全部 24 层注意力/卷积 + 全部 12 层 3× 循环核 + 22 层专家常驻 8 GiB 显存**。  
> ³ 若 HIP 完全不卸载（`-ngl 99`），模型占满显存后会在首次调用 `hipblasCreate` 分配 ~128 MiB 工作区时触发 OOM；若仅卸载 1 层（`blk.23`），`tg128` 达 `25.10 tok/s`，但 `pp512` 激活缓冲触发 PCIe GTT 换页导致预填充从 `548 tok/s` 骤降至 `14.4 tok/s`。Vulkan 因无需 `hipBLAS` 句柄，是唯一在 `8 GiB` 卡上实现 **100% 零卸载全模型常驻（`8,123.6 MiB`）** 的后端。  
> ⁴ `-ot "blk\.([0-5]|1[89]|2[0-3])\.ffn_.*_exps=CPU"`：将全部 12 层单遍外层（Prelude `0..5` + Coda `18..23`）的专家放 CPU，**100% 保留中间 3× 循环核（`blk.6..17`）及全模型稠密层在 GPU**。  
> ⁵ 注：`Intel UHD 770` UMA 核显在 `15.4 GiB` 主机内存下因 Mesa ANV 单缓冲/GTT 配额与 `7.23 GiB` 模型页缓存叠加超出物理空闲水位（报 `ErrorOutOfDeviceMemory`），需 `≥24 GiB` 系统内存方可启用核显加速。

### 核心实验发现

1. **8 GiB 主流显卡成功流畅运行 26.2B 循环 MoE 模型**：
   - 借助 `UD-IQ1_S`（`7.23 GiB`）与双外层专家卸载，单张 **8 GiB RX 9060 XT** 实现了 **`pp512 = 547.95 tok/s`（首字延迟 < 1 秒/512 tok）、`tg128 = 24.96 tok/s`** 的交互级体验，比 12 核 i7-12700 纯 CPU 快 **14.1×（Prefill）** 和 **3.89×（Decode）**。
   - 纯 CPU（`6.41 tok/s`）单步等效访存带宽约为 `2.51 GiB × 6.41 ≈ 16.1 GB/s`，约占本机 STREAM 实测读带宽（`32.88 GB/s`）的 **49.0%**（受限于 128 选 8 离散专家 gather 跨页非连续访存与 `IQ1_S` 码本查表开销）。
2. **循环感知混合卸载（Loop-Aware Offloading）完胜朴素 `-ngl` 层切分**：
   - 在完全相同的显存预算下（甚至**少用 `181.6 MiB` 显存**：`5,528.2 MiB` vs `5,709.8 MiB`），按循环拓扑卸载单遍外层专家（方案 4）相比朴素 `-ngl 15`（方案 5，把 3× 循环核的 `blk.15..17` 留在 CPU 上每步往返执行 3 次）：
     - **Prefill 提速 `+50.2%`（`1.50×`：`298.88 → 449.04 tok/s`）**；
     - **Decode 提速 `+74.6%`（`1.75×`：`11.13 → 19.43 tok/s`）**！
   - 这证明对于 `Inkling-2` 这类循环 MoE 模型，推理引擎的自动内存规划器**绝不能按层号线性截断**，必须按 **`逻辑访问频次 ÷ 字节体积`（价值密度）** 排序：稠密注意力/循环门控 > 循环核专家（`3×`）> 外层专家（`1×`）。

## 4. 原生 `DSpark` 分块投机解码实测与生成质量验证

在 `RX 9060 XT` 循环感知混合卸载 + `--load-mode none` 统一基线下（无投机时显存 `5,772 MiB` / RSS `4,515–4,824 MiB`；加载 `dspark-Inkling-2-Mini-Q8_0.gguf` 后显存 `6,509–6,540 MiB` / RSS `4,720–5,047 MiB`，预留 `>1.5 GiB` 充裕显存），固定 `temperature = 0, seed = 42` 对比三类典型任务：

| 任务场景 | 无投机基线 (`n_max=0`) | **`DSpark` (`n_max=3`)** | 接受率 (`n_max=3`) | **`DSpark` (`n_max=5`)** | 接受率 (`n_max=5`) | 最优有效加速比 |
|---|---:|---:|---:|---:|---:|---:|
| **数学推导**（不定方程 $a^2 - b^2 = 105$ 全解） | `19.08 tok/s` | **`28.67 tok/s`** | **`70.3%`** (`344/489`) | `27.58 tok/s` | `52.9%` (`357/675`) | **`1.50×`（+50.3%）** |
| **Rust 系统编程**（`no_std` 零分配泛型环形缓冲） | `19.13 tok/s` | `22.51 tok/s` | `48.5%` (`378/779`) | **`25.85 tok/s`** | **`47.9%`** (`450/940`) | **`1.35×`（+35.1%）** |
| **高信息密度中文简答**（三句话概括 MoE + 循环架构） | **`19.11 tok/s`** | `17.53 tok/s` | `27.0%` (`167/618`) | `16.53 tok/s` | `21.4%` (`228/1065`) | `0.92×`（低接受率负收益） |

### 关键观察与生成质量评估
1. **高确定性推理显著受益，开放式中文需自适应熔断**：
   - 即使主模型被极限压缩至 `1.56 bpw`（`UD-IQ1_S`）而 `DSpark` 投机器为 `Q8_0`（存在量化分布偏移），在公式推导与 Rust 代码上依然取得 **`48%–70.3%` 的草稿接受率**，将 `5.5 GiB` 显存混合模式的解码速度从 `19.1 tok/s` 直接推高至 **`25.85–28.67 tok/s`**（甚至超越了 `8.0 GiB` 满显存无投机的 `24.96 tok/s`！）。
   - 相反，在高度凝练的中文摘要上接受率降至 `21%–27%`，固定开启 `DSpark` 会产生 `8%–13%` 倒退——这从第三方大模型实战侧面印证了 `tinymodel` 在 `ADR-011` 中设计的 **`SpecController` 在线 EMA 净收益 `< 5%` 自动冷却熔断机制** 的必要性。
2. **输出正确性与 `IQ1_S` 极限量化边界**：
   - **数学推理满分**：模型准确因式分解 $(a-b)(a+b)=105$，验证奇偶性并完整枚举全部四组正整数解 $(53,52), (19,16), (13,8), (11,4)$，无幻觉。
   - **中文概念准确**：三句中文准确概括了门控稀疏路由扩容与共享权重多次迭代加深有效计算的核心机理。
   - **`IQ1_S` 在零容错思考预算控制上的局限**：当通过模板传入 `reasoning_effort = "none"`（`Thinking effort level: 0`）要求跳过思考直接写复杂的 `no_std` `[T; N]` 代码时，`1.56 bpw` 模型未能严格服从 `effort=0` 约束，仍进入超长思维链反复权衡 `T: Copy` 无 `Default` 时的 `MaybeUninit` 初始化方案（改用 `reasoning_effort = "low"` 时正常输出正文）。若用于严肃代码生产且具备 `16 GiB+` 内存/显存，应优先选用 **`UD-IQ3_XXS`（`10.86 GiB`，Top-1 一致率从 `89.4%` 跃升至 `94.7%`，KLD 从 `0.0911` 降至 `0.0269`）** 或 **`UD-IQ4_XS`（`14.65 GiB`，Top-1 `97.7%`）**。

### 端侧微调可行性补充评估
- `Inkling-2-Mini` 虽激活参数仅 5.4B，但因包含 **26.2B 物理权重 + 3 遍循环反向传播图（48 层逻辑激活栈需全部保存以反传梯度穿过 `rank-64` 门控控制器与 128 路 MoE 路由）**，即使采用 4-bit QLoRA + 梯度检查点，训练态显存水位也高达 **`20 – 26 GiB`**。因此本矩阵中仅 **32 GB Apple Silicon** 或 **32 GB RK3588（极慢速研究验证）** 具备内存可行性，8 GB 独显主机与全部手机/树莓派均不支持本地微调，微调应按官方设计走云端平台（如 Tinker）或服务器 GPU。

## 6. 对 `tinymodel` 架构演进的启发（供 M5/M6 参考）

虽然 26.2B 的 `Inkling-2-Mini` 本身超出 `tinymodel` `≤8B` 的目标边界，但本次实测揭示了三项可直接反哺 `tinymodel` **M6（小型端侧 MoE，如 `LFM2-8B-A1B` 或未来 `≤8B` 循环小模型）** 的高价值工程准则：

1. **按“每 Token 逻辑访问频次 ÷ 字节数”做异构显存/内存规划**：本次实测证明，对含共享循环层或 MoE 的混合架构，把循环核与稠密注意力锁在 GPU、仅将单遍稀疏专家留在 CPU（配合 `--load-mode none` 消除页缓存双份驻留），能用 **更少显存换取 `1.75×` Decode 与 `1.50×` Prefill 提速**，同时砍掉 **42% 主机 RSS**。
2. **显存预算规划器必须预留后端运行时工作区安全水位**：本次复现了 ROCm HIP 在显存占用 >98.5% 时触发 `hipblasCreate` OOM 与 `pp512` `38×` GTT 换页断崖，验证了 `tinymodel` `MUST #6`（加载期静态 `ArenaPlanner` 一次性预留全部权重 + KV + 最大批 Scratch，超限直接前置报错而非运行期退化/崩溃）的正确性。
3. **神经网络投机器（MTP / DSpark）同样必须接入在线收益熔断（`SpecController`）**：实测 `DSpark` 在数学与代码上带来 `1.35×–1.50×` 净提速，但在低接受率中文摘要上回退至 `0.87×–0.92×`；无论使用无权重 Suffix 还是带权重 MTP/DSpark，在线 EMA 监控接受率并动态开关都是保障端侧最坏情况不退化的关键闭环。
