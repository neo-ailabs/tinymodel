# 降低推理功耗（能耗 / token）分析

> 日期：2026-11-20  
> 覆盖设备：M4、Pi 5、Pi 4B / Zero 2W、Google Pixel 8（按 `AGENTS.md` §8）。  
> 本文只有 1 组 M4 线程数据是**实测**，其余功耗数字都是**估算**，要按第 5 节的方法测过才能当结论。

---

## 1. 衡量指标：焦耳 / token，不是瓦

**能耗 / token = 平均功率 × 每 token 耗时**。降低功率不一定省电（耗时变长会抵消），提速也不一定省电（多开的核在空转）。不同阶段的规律不一样：

| 阶段 | 瓶颈 | 能耗主要花在 | 省电思路 |
|---|---|---|---|
| decode | 内存带宽 | **DRAM 读取**（每个 token 把全部权重读一遍）+ 核在等内存时的静态功耗 | **少读字节**；带宽喂饱后**不要再加核、不要拉高频率** |
| prefill | 算力 | 乘加运算 | 用每 FLOP 能耗更低的单元（GPU / i8mm / SME2），**算完尽快空闲**（race to idle） |
| 空闲 | — | 线程自旋、轮询 | 及时休眠 |

## 2. 实测：M4 CPU 上线程数和 CPU 时间的关系

`tinymodel bench -m Qwen3.5-0.8B-Q4_0.gguf -n 128 -c 1024`（同样的工作量：pp512 + tg128 + 预热），2026-11-20：

| 线程 | tg128（tok/s） | 相对 1 线程提速 | 整个 bench 的 CPU 总时间（user） | 相对 1 线程的 CPU 时间 |
|---:|---:|---:|---:|---:|
| 1 | 42.6 | 1.00× | 8.35 s | 1.00× |
| 2 | 78.0 | 1.83× | 9.19 s | 1.10× |
| 3 | 103.0 | 2.42× | 10.65 s | 1.28× |
| 4 | 113.5 | 2.67× | 11.90 s | **1.43×** |

- 从 3 线程到 4 线程：decode 只快了 **10%**，CPU 时间却多了 **12%**。带宽已经接近饱和，多出来的核主要在等内存和自旋。
- CPU 时间只能近似代表能耗（核在等内存或自旋时功率比满载低），准确结论要用第 5 节的功率计测量。
- **结论**：省电模式下用 2–3 个线程，用 9–30% 的速度换 14–23% 的 CPU 时间。

## 3. 手段（按收益排序）

### ① 每个 token 少读字节（decode 省电的根本）
- **低比特量化**：Q4_0 每个 token 的读取量约为 Q8_0 的一半，DRAM 能耗也接近减半。
- **LM head**：Qwen3.5 的 `lm_head`（Q6_K，248k 词表）占 decode 时间的 26–30%。可以裁剪词表，或者给 LM head 单独换更低比特的格式（要评估对质量的影响）。
- **投机解码**（MTP / suffix）：一次权重读取验证多个 token。平均每步接受 a 个 token，权重读取的能耗就大致摊薄到 1/(a+1)。这是 decode 阶段**唯一能明显降低每 token 能耗的算法手段**。

### ② 不做重复的工作
- **前缀缓存加状态快照**：多轮对话时不重算历史，prefill 的能耗直接省掉（和首字延迟用的是同一套机制）。
- 遇到 EOS 立即停止；限制最大输出长度；精简系统提示。

### ③ 线程和核心策略
- 线程数按**能效**选，不按最高速度选（见第 2 节）。
- 异构核上，**decode 用中核，prefill 才用大核**（见第 4 节 Pixel 8）。
- macOS 上可以把线程的 QoS 设成 `utility` 或 `background`，让系统把后台生成调度到 E 核。

### ④ 线程池自旋策略
[pool.rs](../../crates/tm-cpu/src/pool.rs) 现在的做法：
- worker 在两次任务之间**自旋 80,000 次（约 0.5 ms）后再休眠**；
- 主线程等待 worker 完成时也是自旋。

decode 期间层与层之间的间隔很短，自旋能省掉唤醒延迟，是对的。但如果下游消费得慢（比如流式输出给 TTS、网络发送），每个 token 之间每个 worker 都要白转 0.5 ms。建议：
- 加一个省电模式，把自旋次数降到几千次；
- 或者在 ARM 上改成 `WFE`/`SEV` 低功耗等待。这类改动属于 `tm-cpu` 里的 `unsafe` / `asm!`，要配测试。

### ⑤ 调频（DVFS）
- **decode 受内存限制，降频几乎不掉速**，而动态功耗大致和 f·V² 成正比。估计 Pi 5 从 2.4 GHz 降到约 1.8 GHz 时，tg 只掉几个百分点，CPU 功耗能省 20–35%（待测）。
- 这和首字延迟的建议相反：首字延迟要求 prefill 跑高频。所以最好**分阶段调频**：prefill 用 `performance`，decode 切到较低频率或 `schedutil`。
- **控制生成速度**：人的阅读速度约 5–10 tok/s。在省电模式下把 decode 限制在 15–20 tok/s，并用更少的核、更低的频率去跑，比全速跑完再空闲更省电（因为是内存受限）。手机上收益最明显。

### ⑥ 选用能效更高的计算单元
- M4：Metal 的 decode（127 tok/s）比 CPU（113 tok/s）快，**每 token 能耗可能更低，但没测过**；prefill 用 GPU 几乎一定更省电。
- Pixel 8：Mali Vulkan 后端排在 M3，到时候要比较 GPU 和 CPU 的 J/token。
- Pi 4B / 5：VideoCore 不适合（见 06 号文档），只能走 CPU。

### ⑦ 温度
芯片越热，漏电功耗越大，还会触发降频，导致耗时更长。树莓派要加散热，手机要避免持续满载。

## 4. 各设备的具体建议

| 设备 | 主要手段 | 估算收益 |
|---|---|---|
| **M4** | 省电模式下 decode 用 2–3 线程，或改用 Metal；后台任务设低 QoS 放到 E 核；prefill 用 Metal | CPU 时间省 14–23%（实测），整机功耗待测 |
| **Pi 5** | decode 阶段降频或用 `schedutil`；用 3 线程；加主动散热避免降频 | CPU 功耗省 20–35%（估算） |
| **RK3588** | `--cluster-policy no-little` 严格绑 4×A76 大核（`0xf0`），避免等 A55 空转；decode 限频至 1.8–2.0 GHz；远期用 Mali Vulkan / RKNPU2 | 8nm 制程每 token 能耗比 Pi 5 低 40–55%（估算） |
| **Pi 4B** | 只跑 decode 的场景不开 `arm_boost`；decode 用 3 线程；Q4_0 加上前缀缓存 | 估算 15–25% |
| **Zero 2W** | 本来带宽就只有约 2 GB/s，**2 个线程可能就够喂饱带宽**，多开只是空转（待测）；低比特量化收益最大 | 待测 |
| **Pixel 8** | ① decode 放在 **4 个 A715 中核**上，不用 X3（X3 每单位性能的功耗明显更高），也不用 A510（会拖住同步）；② 用 Android 的 **PerformanceHint（ADPF）API** 上报每个 token 的目标耗时，让系统选能满足要求的最低频率；③ 控制生成速度；④ 充电时才做 prefill 密集的任务 | 估计每 token 能耗能降 30–50%，要用 ODPM 实测 |

## 5. 测量方法（建议写进 `docs/TESTING.md` 的基准协议）

| 设备 | 方法 |
|---|---|
| M4 | `sudo powermetrics --samplers cpu_power,gpu_power -i 200`，测试期间取平均功率，乘以耗时再除以 token 数 |
| Pi 5 | `vcgencmd pmic_read_adc`，读各路电压和电流计算功率；或者用 USB-C 功率计测整机 |
| Pi 4B / Zero 2W | 板上没有功率传感器，只能用 USB 串联功率计测整机 |
| Pixel 8 | 用 Perfetto 的 **ODPM 功耗轨道**（`android.power` 数据源，可以分别看大核、中核、小核和 DDR 的功耗）；粗略测量可以读 `/sys/class/power_supply/battery/current_now` 和 `voltage_now` |

统一报告：**J/token（decode）、J/token（prefill）、空闲功率**，并记录线程数、频率和温度。
